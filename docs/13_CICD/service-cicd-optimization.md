# 서비스 CI/CD 최적화 정리

## 적용 범위

이 문서는 현재 전체 서비스에 적용한 CI/CD 최적화 내용을 정리한 문서입니다.

적용 대상 서비스는 아래와 같습니다.

- `api-gateway`
- `admin`
- `ai`
- `order`
- `payment`
- `product`
- `settlement`
- `user`

이번 최적화의 목표는 아래와 같습니다.

- 환경변수 반영과 애플리케이션 배포를 분리합니다.
- 리스크가 낮은 항목부터 우선 적용합니다.
- 기존 Docker 빌드 방식은 최대한 유지합니다.

## 적용한 내용

### 1. 환경변수 반영을 소스 배포와 분리했습니다

이제 각 서비스의 일반 CD 워크플로에서는 env 파일을 직접 적용하지 않습니다.

현재 역할은 아래와 같이 분리되어 있습니다.

- 서비스별 CD 워크플로
  - jar 빌드
  - Docker 이미지 빌드 및 푸시
  - 배포 스크립트와 manifest 복사
  - Kubernetes manifest 배포
- `Deploy Environment`
  - 공통 ConfigMap / Secret 반영
  - 서비스별 ConfigMap / Secret 반영
  - 필요한 경우 선택한 서비스 또는 전체 서비스 재시작

이렇게 분리하면 코드 배포와 설정 배포의 책임이 서로 섞이지 않아 운영이 단순해집니다.

### 2. 동일 브랜치의 중복 배포를 방지했습니다

각 서비스 CD 워크플로에 `concurrency`를 추가했습니다.

효과는 아래와 같습니다.

- 같은 브랜치에서 연속 배포가 발생해도 최신 실행 기준으로 정리됩니다.
- self-hosted runner에서 겹치는 배포 충돌 위험이 줄어듭니다.

### 3. Gradle 캐시를 적용했습니다

각 서비스 CD 워크플로에서 `actions/setup-java@v5`와 `cache: gradle`을 사용합니다.

효과는 아래와 같습니다.

- 반복 실행 시 의존성 다운로드 시간이 줄어듭니다.
- 기존 Gradle 빌드 명령은 유지하면서 속도만 개선할 수 있습니다.

참고로 `clean`은 안정성을 위해 그대로 유지했습니다.

### 4. CD에서 전체 저장소 복사를 제거했습니다

기존에는 저장소 전체를 `/home/ubuntu/apps/repo`로 복사한 뒤 다시 필요한 파일만 꺼내 쓰는 구조였습니다.

현재는 아래 방식으로 단순화했습니다.

- self-hosted runner에서 필요한 파일만 체크아웃합니다.
- 체크아웃한 워크스페이스에서 바로 배포 경로로 복사합니다.

복사 대상은 아래와 같습니다.

- `.github/scripts/deploy-app.sh`
- 각 서비스의 `.github/k3s/*-service.yml`

효과는 아래와 같습니다.

- 중복 복사 단계가 사라집니다.
- deploy job의 I/O가 줄어듭니다.
- 최종 배포 경로는 기존과 동일하게 유지됩니다.

### 5. deploy job에 sparse checkout을 적용했습니다

deploy job에서는 필요한 파일만 내려받도록 범위를 줄였습니다.

서비스 CD deploy job은 아래 경로만 체크아웃합니다.

- `.github/scripts`
- 해당 서비스의 `.github/k3s/<service>-service.yml`

`Deploy Environment`는 아래 파일만 사용합니다.

- `.github/scripts/apply-env.sh`

효과는 아래와 같습니다.

- 체크아웃 범위가 작아집니다.
- runner의 디스크 사용량과 I/O가 줄어듭니다.

### 6. 공통 배포 스크립트를 단순화했습니다

`deploy-app.sh`는 이제 manifest 배포 전용 스크립트입니다.

현재 수행하는 작업은 아래와 같습니다.

- manifest 읽기
- 이미지 변수 치환
- Kubernetes apply
- rollout 확인
- 실패 시 진단 로그 출력

아래 항목은 제거했습니다.

- env 파일 처리
- ConfigMap / Secret 생성
- config 변경 여부 판단
- restart 분기 처리

## 의도적으로 적용하지 않은 내용

이번 단계에서는 아래 항목을 적용하지 않았습니다.

### 1. Docker Buildx

적용하지 않았습니다.

이유는 아래와 같습니다.

- 이미지 빌드 경로 자체가 바뀝니다.
- 검증 과정에서 원인 분리가 어려워질 수 있습니다.

### 2. Docker layer cache

적용하지 않았습니다.

이유는 아래와 같습니다.

- 속도 개선 효과는 있지만 안정성 검증이 먼저 필요합니다.
- 이번 단계는 저리스크 최적화가 우선입니다.

### 3. Gradle `clean` 제거

적용하지 않았습니다.

이유는 아래와 같습니다.

- 현재는 속도보다 예측 가능한 동작이 더 중요합니다.

### 4. manifest 변경 감지 로직 개편

적용하지 않았습니다.

이유는 아래와 같습니다.

- 이번 단계에서는 기존 동작을 최대한 유지했습니다.
- 구조가 안정된 뒤 별도 작업으로 개선하는 편이 안전합니다.

## 기대 효과

이번 최적화로 속도 개선과 운영 단순화 효과를 함께 기대할 수 있습니다.

예상 효과는 아래와 같습니다.

- env만 바뀐 경우 별도 흐름으로 반영할 수 있습니다.
- 설정 변경과 소스 배포를 분리해 운영 판단이 쉬워집니다.
- 전체 저장소 복사를 제거해 deploy job 부담이 줄어듭니다.
- Gradle 준비 시간이 단축됩니다.
- 헬스체크 대기 시간이 일부 줄어듭니다.

실제 배포 기준으로는 기존 약 5분대에서 3분대로 줄어든 것을 확인했습니다.

## 현재 운영 기준

현재 운영 방식은 아래와 같습니다.

- 코드가 바뀌면 서비스별 CD를 실행합니다.
- env가 바뀌면 `Deploy Environment`를 실행합니다.
- 전체 재시작이 필요하면 `service = all`을 사용합니다.

현재 구조를 기준으로 이후 변경도 특별한 이유가 없다면 같은 방향으로 유지하는 것이 안전합니다.
